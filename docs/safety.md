# TikTok Boost — Safety Design

Boosting a post spends the customer's money and creates objects in the customer's TikTok ad account. This document lists the risks considered, what the implementation does about each, how it is verified, and what remains.

## Risks and mitigations

| #   | Risk                                                                                                         | Mitigation                                                                                                                                                                                                                                                                           | Where                          | Verified by                                                                 |
| --- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ | --------------------------------------------------------------------------- |
| 1   | **A mistaken request costs money** (wrong budget, typo, wrong post, past dates)                              | Strict validation before any TikTok call: unknown fields rejected, money limited to 2 decimals and checked in integer cents, dates need a timezone and must be in the future, TikTok minimums, age ranges, exactly one post identifier. Every problem in one `details` string (101). | `schema.ts`                    | `boost-schema.test.ts` (64 tests)                                           |
| 2   | **Unbounded spend**                                                                                          | `endDate` is required, so every boost has a computable worst case (`maxSpend`) that is returned to the caller.                                                                                                                                                                       | `schema.ts`                    | schema + endpoint tests                                                     |
| 3   | **Large or runaway spend** (bug in a client loop, fat-fingered budget)                                       | Server-side caps on worst-case spend: per boost (`MAX_SPEND_PER_BOOST`) and per profile across running boosts (`MAX_SPEND_PER_PROFILE`) → 604 before any TikTok call.                                                                                                                | `service.ts`                   | `boost-safety.test.ts`                                                      |
| 4   | **Two concurrent boosts both pass the profile cap**                                                          | The cap is re-checked inside an `IMMEDIATE` transaction together with the boost insert.                                                                                                                                                                                              | `repository.ts`                | race test: two parallel boosts, exactly one created                         |
| 5   | **Client retry creates a second ad** (timeout, network error, double click)                                  | `Idempotency-Key`: the stored response is replayed; a key reused for a different body → 608; a concurrent duplicate → 609. The claim survives client disconnects. Retryable failures aren't stored, so retries do run again.                                                         | `middleware/idempotency.ts`    | `idempotency.test.ts`, endpoint tests                                       |
| 6   | **Our retry to TikTok creates a duplicate campaign** (TikTok processed the create but the response was lost) | Writes that fail ambiguously (timeout, 5xx, unparseable 200) are never retried. The object is looked up by its unique name (`{adName} - {boostId}`); a deterministic TikTok `request_id` is sent as a second dedupe layer. Only rate-limit rejections (not processed) are retried.   | `http-client.ts`, `service.ts` | HTTP client tests; "lost response" service tests                            |
| 7   | **Money spent on a half-built boost**                                                                        | Campaign, ad group and ad are all created **disabled**; they are enabled only once all three exist (ad → ad group → campaign, top-level switch last), and only for `status: "active"`.                                                                                               | `mapper.ts`, `service.ts`      | service tests assert every create payload is `DISABLE` and the enable order |
| 8   | **Failure leaves junk or live objects in the customer's account**                                            | Compensating rollback, children first: delete, falling back to disable. Anything left is recorded on the boost (`cleanup_failed`) and reported as 610 with IDs, plus an explicit "pause it now" warning if anything could still be enabled.                                          | `service.ts`                   | rollback tests at every step; orphan and enabled-orphan tests               |
| 9   | **Boosting a post the customer doesn't control**                                                             | Own posts: Ayrshare `postId` must belong to the profile, and `tiktokPostId` is checked against the linked identity (`identity/video/info`). Spark codes: TikTok authorizes the code, and the creator's authorization must outlast `endDate`.                                         | `service.ts`                   | pre-flight tests (603/602)                                                  |
| 10  | **Wrong currency** — a budget in USD charged as another currency                                             | The linked advertiser's currency must be USD, otherwise 601 before anything is created.                                                                                                                                                                                              | `service.ts`                   | pre-flight test                                                             |
| 11  | **Cross-tenant access**                                                                                      | API key → account; `Profile-Key` must belong to that account (same 613 for unknown and foreign keys); boost lookup is profile-scoped (615).                                                                                                                                          | `authenticate.ts`, `routes.ts` | auth and lookup tests                                                       |
| 12  | **Credential leakage**                                                                                       | API/Profile keys stored only as SHA-256 hashes; pino redacts keys, tokens and Spark codes; audit data passes through `redactSecrets`; Spark codes are masked on the boost row and never returned.                                                                                    | `secrets.ts`, `logger.ts`      | logger, secrets and audit tests; DB dumps checked for raw values            |
| 13  | **Accidentally hitting production**                                                                          | `TIKTOK_MODE` must match `TIKTOK_BASE_URL`'s host (sandbox ↔ live), checked at startup; the default is `mock`.                                                                                                                                                                       | `config/env.ts`                | config tests                                                                |
| 14  | **TikTok rate limits** (sandbox: 1 QPS)                                                                      | Outbound calls are spaced by `TIKTOK_MAX_QPS`; rate-limited calls retry with backoff; 606 tells the client to retry with the same key.                                                                                                                                               | `rate-limiter.ts`              | rate limiter + HTTP client tests                                            |
| 15  | **No trail when something goes wrong**                                                                       | Boost row written before the first TikTok write and updated after every step; `audit_events` records rejections, dry runs, start, outcome, every TikTok call (with TikTok `request_id`) and replays, correlated by `X-Request-Id` and boost ID. Audit writes never break a boost.    | `audit-log.ts`, `service.ts`   | audit tests                                                                 |
| 16  | **"Try before you buy"**                                                                                     | `dryRun: true` runs every check (caps and pre-flight) and returns the exact plan, with no TikTok writes (Spark codes inspected, not authorized) and no boost row.                                                                                                                    | `service.ts`                   | dry-run tests                                                               |

## Residual risks and what production would add

- **Unverified TikTok details.** Enum values, response shapes and error codes marked ⚠️ have not been confirmed against TikTok (see [Verification before launch](./tiktok-boost.md#verification-before-launch)). A wrong value fails safely (TikTok rejects the request and the boost is rolled back), but must be confirmed before launch.
- **Access tokens at rest.** TikTok access tokens are stored in plain text in SQLite for this exercise; production would encrypt them with a KMS-managed key.
- **Single-process assumptions.** The rate limiter and in-progress idempotency claims are correct for one process. Several instances need a shared limiter keyed per advertiser (e.g. Redis) and a shared database. The SQLite transactions are already safe across processes on one host.
- **Crash mid-boost.** If the process dies between creating objects and recording the outcome, the boost row stays `in_progress` with the TikTok IDs already written. The objects are disabled unless activation had begun. Production would add a sweeper that reconciles stale `in_progress` boosts and alerts on `cleanup_failed` ones.
- **Spend velocity.** The caps limit worst-case exposure per profile, not how many boosts an account starts per hour; a per-account rate limit on this endpoint would be a cheap addition.
- **After creation.** TikTok review status, delivery and actual spend aren't tracked; updates, pauses and deletes are out of scope for this endpoint.
